Closing this for real needs foreign-currency support added to the sales-order/purchase-order pipeline itself first (request records, domain fields, service propagation from order through shipment/receipt to invoice/bill, and UI fields on `Operations.razor`'s order forms) -- a materially larger, separate piece of work than a browser fixture, and arguably its own FX-TRANSACTIONS sub-slice rather than an extension of sub-slice 4. Not attempted; scope and prioritize it as its own slice against the rest of the roadmap rather than folding it into this one.
5. **In progress -- Foreign recurring documents:** the invoice/bill recurring-template pipeline (`SaveRecurringInvoiceTemplateAsync`/`SaveRecurringVendorBillTemplateAsync`/`GenerateDueRecurringDocumentsAsync`) previously rejected any foreign-currency template outright, with the excuse that "each occurrence requires a current retained rate." Fixed by selecting a rate per generated occurrence instead of freezing one on the template, matching every other FX entry point in this codebase's existing invariant that a human always explicitly picks the specific retained rate -- there is no auto-pick-latest-rate helper anywhere, by design, so a fully-automatic per-occurrence pick would have violated that invariant, and a frozen template rate would have been worse (an ever-more-stale rate reused forever). A foreign template may now be saved (rejecting only an attempt to supply a fixed `ExchangeRateId` on the template itself, via a new `allowPendingForeignRate` branch in `ResolveTransactionRateAsync` that returns a placeholder factor for template-time structural validation only); `GenerateDueRecurringDocumentsAsync` always strips any `ExchangeRateId` from a generated occurrence's payload (defense in depth); and a new `AssignRecurringOccurrenceRateAsync` service method (`BrassLedger.Infrastructure/Accounting/AccountingTransactionService.cs`, `AssignRecurringOccurrenceRateRequest` in `TransactionModels.cs`, a `/recurring-subledger-documents/assign-rate` API route) lets a preparer assign a real, dated rate to one generated occurrence before it can be approved -- `ApproveSubledgerDocumentAsync`'s existing validation already fails closed on a foreign occurrence with no rate, unchanged. `SubledgerDocumentWorkflowSnapshot` gained `TransactionCurrency`/`RequiresRateAssignment`/`TransactionDate` so the UI can show which generated drafts still need a rate; `Receivables.razor`/`Payables.razor` gained an inline rate picker and "Assign rate" button for exactly those drafts, and their own "Save recurring template" actions now always send a null rate regardless of whatever the shared invoice/bill form's own rate field holds. `BrassLedger.Infrastructure.Tests.WorkspaceInitializationTests.ForeignRecurringInvoiceTemplate_NeverFreezesARateAndRequiresOnePerGeneratedOccurrence` proves: a template carrying an explicit rate is rejected; a template without one succeeds; both generated occurrences report `RequiresRateAssignment`; approval fails before a rate is assigned; a rate whose effective date is after the occurrence's own date is rejected; a rate can be assigned exactly once (a second assignment attempt is rejected); and the two occurrences end up posted at two different, independently selected rates -- proving this is "a rate per occurrence," not "a rate per template" reused silently. Full solution build clean, 0 warnings.

   Browser evidence is now built. `BrassLedger.Web.E2E.Tests.RecurringDocumentWorkflowTests` adds the recurring-document workflow's first browser coverage of any kind (previously none existed, domestic or foreign): `ReceivablesPage`/`PayablesPage` gained `SaveRecurringInvoiceTemplateAsync`/`SaveRecurringVendorBillTemplateAsync`, `GenerateDueRecurringInvoiceDraftsAsync`/`GenerateDueRecurringBillDraftsAsync`, and `AssignRecurringOccurrenceRateAsync` page-object methods covering the whole template → generate → (assign rate) → approve → post lifecycle. `RecurringInvoiceTemplate_GeneratesDueOccurrenceThatApprovesAndPosts` and `RecurringVendorBillTemplate_GeneratesDueOccurrenceThatApprovesAndPosts` prove the domestic path on both sides; `ForeignRecurringInvoiceTemplate_RequiresRateAssignmentBeforeApproval` proves the FX extension end to end in a real browser -- a generated foreign occurrence's Approve button is confirmed absent before a rate is assigned, an assigned rate unblocks it, and the posted invoice's transaction- and base-currency amounts (`100.00 CAD` / `75.00 USD`) confirm the assigned 0.75 rate actually applied.

   Building this found and fixed a real, previously-undetected production bug: the inline rate-picker's `<InputSelect>` used `@bind-Value="GetOccurrenceRateSelection(workflow.Id).ExchangeRateId"` -- a method call in the bound expression path. Blazor's `InputBase<T>.NameAttributeValue` calls `ExpressionFormatter.FormatLambda` on that expression to compute the rendered `name` attribute, and that formatter throws `InvalidOperationException: Method calls cannot be formatted` for anything beyond a simple member-access chain. The exception was silently swallowed into the app's page-level error boundary ("That screen hit a snag"), so this only surfaced once a real foreign occurrence's row actually needed to render the picker -- invisible to every unit test, since none of them render Razor components. No C# unit test could have caught this; only a real browser render could. Fixed in both `Receivables.razor` and `Payables.razor` by replacing the `InputSelect<Guid?>` with a plain native `<select>` using one-way `value="@expr"` binding plus an explicit `@onchange` handler, which never goes through `ExpressionFormatter`.

   **Not yet `Verified`:** the new `AssignRecurringOccurrenceRateAsync` endpoint specifically still lacks its own dedicated authorization-denial (a caller without `SubledgerPrepare`/module-manage permission), cross-company isolation, and concurrent-assignment negative-matrix coverage -- the unit test above proves sequential double-assignment is rejected, not a true concurrent race. Close that matrix before marking this sub-slice `Verified` outright.
