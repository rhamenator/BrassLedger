# Production readiness

BrassLedger is under active production-readiness development. A successful build or the presence of a screen does not by itself establish that a workflow is suitable for a real business. This report separates verified behavior from work that remains incomplete or requires external review.

## Verified checkpoints

### Controlled inventory purchasing

The inventory purchasing workflow currently supports controlled purchase requisitions, purchase orders, partial receiving, multiple partial supplier invoices for one receipt, independent invoice review, posting, exact reversal, landed-cost allocation, and supplier returns.

Purchase-invoice matching records receipt accrual, actual invoice value, matched quantity, unmatched quantity variance, and price variance separately. Draft, submitted, approved, rejected, posted, cancelled, and reversed states retain actor, time, reason, source, and journal provenance. The preparer cannot decide a match, and the reviewer cannot post it. Supplier returns distinguish invoiced quantities from uninvoiced receipt accruals and can consume quantities across multiple partial invoices.

SQLite and PostgreSQL have separate versioned migrations for this schema. Existing receipt-linked bill and supplier-return data is backfilled. Databases that already contain the new schema but have lost migration history are adopted without replaying incompatible column additions. Downgrade across this migration is deliberately prohibited because the former one-bill-per-receipt schema cannot preserve the new provenance.

### Controlled receivables and payables posting

Customer invoices and ordinary vendor bills enter through draft, approval, and posting workflows; neither the HTTP API nor the public accounting application-service contract exposes a direct ordinary posting operation that bypasses review. Integrations and future server-side components therefore have to create drafts. Built-in Receivables and Payables Preparer, Approver, and Poster roles permit least-privilege assignments. A preparer cannot approve or reject the same document as its reviewer, and its approver cannot post it.

Posting the journal, account and subledger balances, source invoice or bill, workflow state, and audit evidence is one database transaction. A forced source-document insertion failure proves that the earlier journal and balance changes roll back and the workflow remains approved for correction or retry. Repeating a completed request returns the original source-document ID without posting again; concurrent attempts produce exactly one source document and one journal entry. These controls are covered by infrastructure and API authorization regressions on 2026-08-26.

Saving and approving a draft now execute the retained posting payload inside a disposable database transaction and explicitly roll it back, so invalid references, distributions, dates, control-account rules, credit limits, and corrupted payloads are rejected before approval without changing the ledger. An authorized reviewer can reject a draft or approved document with a required reason and optimistic concurrency token. The reason, reviewer, time, and immutable audit event remain visible. A preparer corrects it by saving the same invoice number, or the same vendor and bill number; the workflow is revised in place, returns to Draft, retains before-and-after audit evidence, and must pass independent approval and posting again. SQLite and PostgreSQL migrations add the review fields, support lost-history adoption, and prohibit downgrade that could delete reviewer provenance.

Vendor-scoped external invoice numbers now apply consistently to drafts, recurring templates, generated drafts, posted bills, purchase-invoice matches, and landed-cost bills. Two vendors may both issue `1001`; a second `1001` for the same vendor is rejected before review. Versioned SQLite and PostgreSQL migrations backfill historical workflow identity from retained request data, support lost-history adoption, and block unsafe downgrade.

### Controlled general-journal posting

Ordinary general journals now enter only through draft, approval, and posting; neither the HTTP API nor the public accounting application-service contract exposes the former direct-post operation. The preparer cannot approve or reject the same journal, and its approver cannot post it. Reviewers can reject a draft or approved-but-unposted ordinary journal with a required reason and current concurrency token. Correction revises the same journal identity, resets it to Draft, and retains its previous header, lines, status, and decision in audit evidence. Generated source-workflow journals cannot be edited or rejected through the general-journal screen.

QuickBooks CSV journal imports create controlled drafts atomically with their import batch and provenance instead of changing balances. Invalid line polarity, unavailable or control accounts, imbalance, and duplicates are rejected. Only posted general journals are exported. SQLite and PostgreSQL migrations retain journal review decisions and prohibit destructive downgrade. Service, API, component, and browser regressions cover stale review, self-approval, self-rejection, approver self-posting, correction, posting, reversal, import draft behavior, and the three-user rendered workflow on 2026-08-26.

### Controlled department and class dimensions

Department and Class are distinct company-scoped, hierarchical, effective-dated accounting dimensions with controlled maintenance, optimistic concurrency, permissions, lifecycle, and audit history. New activity requires the correct active dimension type to be effective on the transaction date. A parent must belong to the same company and type, and hierarchy cycles are rejected. Inactive or expired values remain available to describe posted history and to preserve exact corrective reversals, but cannot receive new activity.

Department and Class propagate through ordinary journals, invoices, bills, quotes, sales orders, purchase requisitions, purchase orders, receipts and invoice matching, customer and supplier returns, payroll time and earnings, payroll burden allocation, project billing, fulfillment, credits, posting, and reversal. Workspace drill-downs resolve their codes, and the corresponding screens provide controlled selectors. QuickBooks journal and zero-tax invoice CSV round trips retain both values. `Class` maps to the BrassLedger Class dimension rather than Project; `Location` and `Business Unit` are accepted Department aliases.

SQLite and PostgreSQL have provider-specific versioned migrations for the tracking master, journal attribution, and all source-line attribution. Lost-history adoption verifies every affected table's columns and indexes before recording the migrations, and destructive downgrade is deliberately prohibited. Verification completed on 2026-08-27: the Release build succeeded with zero warnings and errors; 194 SQLite/default infrastructure tests passed with nine PostgreSQL-only skips; 203 of 203 disposable PostgreSQL infrastructure tests passed; 34 API tests, 10 web component tests, and 31 Chromium end-to-end tests passed; and both EF provider models reported no pending changes.

### Effective-dated consolidation ownership

Consolidation membership is retained as non-overlapping effective-dated ownership periods rather than a replaceable current percentage. Only an active owner of the parent and every member company can configure a group or period. Initial, successor, corrected, and closed periods retain their own concurrency token; a membership change also advances the group token so concurrent overlapping additions cannot both commit. Accepted changes create company-scoped audit events, and the consolidated balance foundation selects the ownership percentage effective on its requested as-of date.

The Administration page supports initial periods and later add/edit/close work. The API rejects mismatched group routes, foreign or non-owned companies, invalid percentages and dates, overlaps, stale edits, and conflicting concurrent writes. Existing memberships migrate to open historical periods with nonblank concurrency tokens. SQLite and PostgreSQL use provider-specific versioned migrations, lost-history adoption checks all new columns and the revised unique index, and downgrade is prohibited because the former schema could not retain multiple periods.

Verification completed on 2026-08-27: the Release solution build succeeded with zero warnings and errors; both EF provider models reported no pending changes; the complete SQLite/default infrastructure suite passed 194 tests with nine provider-only skips; the then-current complete PostgreSQL suite passed 203 of 203 tests; the added PostgreSQL concurrent-overlap regression passed separately; all 35 API tests and 10 component tests passed; and all 31 Chromium end-to-end tests passed against the same fresh Release web assembly. Translation-rate policy, consolidation adjustments, noncontrolling-interest presentation, and intercompany eliminations remain open and are not implied by this ownership checkpoint.

### Explicit consolidation account mappings

Consolidated balances no longer merge accounts because local numbers, names, or types happen to match. Every material member-company balance must resolve through one explicit source-to-reporting mapping effective on the report date. Mapping identity retains the group, member company, source account, reporting number/name/type, effective dates, active state, concurrency token, operator, and audit event. Overlapping source mappings are rejected. During overlapping periods, one reporting number cannot carry inconsistent names or account types. A mapping cannot be moved to a different source account; close it and add a successor instead.

The Administration page lists accounts from every owned member company, including inactive accounts with possible history, suggests their local identity for deliberate review, and supports add, edit, close, and successor mapping workflows. Unmapped, multiply mapped, or type-inconsistent nonzero balances are excluded with report warnings that identify the company, account, source-currency amount, and reason. Zero balances do not create warning noise. Closing or deactivating a mapping requires an effective-through date, and historical reports continue to use the retained mapping that was effective at their as-of date.

SQLite and PostgreSQL have provider-specific versioned migrations with restrictive group, company, and account provenance, lost-history adoption, and prohibited destructive downgrade. Verification completed on 2026-08-27: the Release build succeeded with zero warnings and errors; both EF provider models reported no pending changes; the SQLite/default infrastructure suite passed 194 tests with 10 PostgreSQL-only skips; the PostgreSQL suite passed 204 of 204 tests including concurrent overlapping ownership and mapping attempts; all 35 API tests and 10 component tests passed; and all 31 then-current Chromium end-to-end tests passed against the same fresh Release assembly. Typed translation and CTA are addressed by the following checkpoint; noncontrolling interest, controlled consolidation adjustments, intercompany elimination, and complete consolidated statements remain open.

### Controlled consolidation translation and CTA

Exchange-rate evidence is now explicitly typed as closing, period average, or historical. Average rates retain a non-overlapping coverage period; closing observations apply at the report date; historical observations apply at each journal line's posting date. Every rate retains its source label, optional source reference, retrieval date, active approval state, concurrency token, operator, and audit event. Only the active-company owner can maintain rates, stale corrections fail, and reports neither substitute one rate type for another nor silently choose between conflicting direct and inverse series.

Each effective account mapping retains its translation method. Assets and liabilities default to closing, revenue and expenses to average, and equity to historical. A reporting account must keep the same name, type, and method during overlapping periods. A selected report period must balance in each member's source currency before CTA is allowed. Any unmapped balance, missing typed rate, ambiguity, or unclosed source-period imbalance produces a precise warning and suppresses CTA. A complete report inserts the translation-only imbalance into a dedicated, non-colliding CTA equity account configured on the group and exposes both the method and adjustment.

SQLite and PostgreSQL have provider-specific migrations that preserve legacy rates as approved closing observations and backfill legacy mapping methods by account type. Lost-history adoption verifies the typed-rate index and policy columns, and destructive downgrade is prohibited. This checkpoint completes the controlled translated-balance foundation only. Noncontrolling-interest presentation, retained consolidation adjustments, intercompany matching and eliminations, and complete consolidated financial statements remain open.

Verification completed on 2026-08-27 against one fresh out-of-tree Release build: the solution compiled with zero warnings and errors; SQLite/default infrastructure passed 194 tests with the expected 10 PostgreSQL-only skips; the complete disposable PostgreSQL 16 run passed 204 of 204 tests with no skips, including concurrent exchange-rate corrections; API integration passed 35 of 35 tests; web components passed 10 of 10 tests; and Chromium end-to-end passed 32 of 32 tests, including the new typed-average-rate administration workflow. Both provider models reported no pending EF changes, migration downgrade protection passed, and focused calculation coverage proved different closing, average, and historical factors, inverse rates, ownership, CTA balancing, overlap rejection, missing-type rejection without fallback, and historical as-of selection.

### Project ledger dimensions

Projects now have company-scoped customer, schedule, billing-method, contract, budget, retainage, lifecycle, concurrency, and audit controls. They also support hierarchical phases/tasks, reusable cost codes, and dated budget/forecast allocations by expense account and those dimensions. Only active same-company projects and dimensions accept new source activity. Project, phase, and cost-code attribution propagate through journals, invoice and bill lines, sales and purchasing documents, quote and requisition conversion, shipment cost and revenue, invoice matching, customer and supplier returns, timecards, payroll expense allocation, project billing, and reversals. Closing is blocked by open orders, requisitions, or timecards; reopening requires a reason. Posted expense and revenue lines, rather than editable project summary fields, drive project cost, revenue, and margin. Unreceived purchase-order value drives commitments. Exact totals use the full posted project ledger while the workspace drill-down is bounded to 250 recent lines.

QuickBooks journal and zero-tax invoice CSV paths preserve optional project/job, phase/task, and cost-code values. Imports require the phase to belong to the selected active project and the cost code to be active in the same company; unknown, ambiguous, inactive, dimension-without-project, or other-company references reject the batch instead of silently dropping attribution. Versioned SQLite and PostgreSQL migrations preserve source, billing, and ledger attribution and prohibit destructive downgrade. Service, API, component, migration, and cross-provider verification cover project isolation, hierarchy, budgeting, concurrency, lifecycle, accounting derivation, payroll allocation, billing, return and reversal propagation, and CSV round trips.

Controlled project change orders provide draft, submission, independent decision, rejection correction, cancellation, stale-project detection, immutable approved history, and atomic contract/budget revision. Controlled project billing now derives fixed-price progress, milestones, approved or payroll-consumed time, and unreversed posted cost-plus/reimbursable cost into previewed receivables drafts. Effective-dated labor rates, contract caps, preview fingerprints, source reservations, approval-time project/source revalidation, three-operator invoice control, rejected correction, cancellation, void synchronization, retainage withholding, partial retainage-release invoices, separate retainage-receivable posting, aging, and control-account reconciliation are enforced. Initial posting recognizes gross revenue, while release posting transfers value from retainage to ordinary receivables without recognizing revenue twice; voids reverse those movements in dependency order.

Projects can use as-billed, cost-to-cost, reviewed manual-percentage, or completed-contract recognition. As-billed projects retain invoice-driven revenue; controlled cumulative WIP schedules recognize revenue independently of billing for the other three methods. A retained preview records contract, cost, estimate, completion, earned revenue, gross billing, prior and desired contract positions, the incremental revenue true-up, source fingerprint, and project concurrency token. Preparation, independent approval, separate posting, rejection, correction, cancellation, latest-schedule-only exact reversal, closed-period controls, and contract-asset and contract-liability reconciliation are enforced. The same revenue account must remain in use while unreversed WIP history exists, and completed-contract WIP must be reversed before its project can reopen. SQLite and PostgreSQL have versioned migrations with lost-history adoption and destructive downgrade protection. Multiple performance obligations, variable consideration, expected-loss provisions, additional user-defined transaction dimensions, and full historical project export remain incomplete; see the [project accounting guide](project-accounting-guide.md).

## Known limitations and unverified areas

The following areas are not yet proven complete against the project definition of done:

- The representative-business acceptance scenario has not passed as one uninterrupted install-to-restore workflow.
- The ordinary AR/AP draft-to-post path is controlled, rejectable, correctable, and retry-safe, but complete AR, AP, banking, payroll, inventory, fixed assets, period-end, multi-currency, consolidation, and reporting acceptance matrices remain to be audited against the required positive, negative, authorization, isolation, rounding, concurrency, and reversal cases.
- Project hierarchy, phase/task, cost-code, department, and class dimensioning, dated budgets/forecasts, lifecycle, derived actuals, purchase commitments, recent-ledger drill-down, controlled change orders, dimension-preserving source-derived billing, separate retainage receivables, release, aging, cumulative WIP, independent revenue recognition, exact reversal, and control reconciliation are implemented. Multiple performance obligations, variable consideration, expected-loss provisions, additional user-defined transaction dimensions, and full historical ledger export are not yet complete.
- Tax runtime packages for every state and the District of Columbia require a source-by-source completion audit, executable boundary tests, review, and explicit activation. Captured or LLM-assisted interpretations are not regulatory approval.
- Local payroll-tax coverage, reciprocity, convenience-of-employer rules, filing outputs, and multi-work-location allocation require jurisdiction-specific verification by qualified payroll/tax reviewers.
- QuickBooks and other interchange paths require a capability-by-capability audit of mapping, dry runs, idempotency, duplicate handling, rejection correction, reconciliation totals, and round trips. QuickBooks Online production synchronization additionally depends on provider credentials and approval.
- Clean install, supported historical upgrades, encrypted off-machine backup, restore to a clean installation, uninstall, installer signing/notarization, SBOM, checksums, and release provenance have not all been rehearsed as a release gate.
- Repository-wide formatting verification currently reports pre-existing whitespace debt in files outside the controlled invoice-matching checkpoint. Changed-file whitespace and `git diff --check` pass, but the broader formatting baseline still needs remediation.
- Independent human accounting, payroll-tax, security, accessibility, and release review remains required before production approval.

## External release blockers

- Official tax publications and professional review are required before activating jurisdiction packages for production payroll.
- QuickBooks Online OAuth credentials and provider approval are required for a live synchronization rehearsal.
- Platform signing/notarization credentials are required for distributable Windows and macOS packages.
- A business-approved backup destination and encryption-key custody procedure are required for an off-machine restore rehearsal.

This document must be updated whenever a checkpoint is added, invalidated, or independently verified. Claims move out of the limitations section only when current authoritative evidence covers the full stated workflow.
